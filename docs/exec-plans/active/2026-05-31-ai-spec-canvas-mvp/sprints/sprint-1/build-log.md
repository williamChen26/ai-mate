### Modularity & Readability Notes
Schemas are declarative and isolated in `src/schemas.ts`; public inferred types live in `src/types.ts`; graph-level semantic validation stays in `src/validation.ts`; JSON Schema artifact behavior stays in `src/json-schema.ts` and `src/export-schema.ts`; consumers use `src/index.ts` as the stable public boundary.

The validation module keeps structural Zod parsing separate from graph-level checks that JSON Schema cannot express, specifically duplicate record ids and missing edge endpoint references. JSON Schema export is explicit rather than generated from recursive Zod metadata, which keeps the machine-readable artifact stable for external tooling and future AI consumers. Tests are written as behavior documentation for valid graph preservation, invalid graph rejection, inspectable issue data, and schema export.

No oversized file was introduced. No Next.js app, tldraw code, graph mutation operation layer, persistence, AI generation, PRD ingestion, or UI code was added.

### Decisions Made
- Used `schemaVersion: "1.0.0"` as a literal initial protocol version because Sprint 1 explicitly excludes migrations.
- Modeled metadata as JSON values, not arbitrary JavaScript values, so external protocol consumers receive serializable extension fields.
- Treated node ids and edge ids as one graph-record namespace by rejecting node/edge id collisions, matching the contract's duplicate graph record id requirement.
- Kept JSON Schema export explicit instead of relying on recursive Zod conversion because external tools and future AI consumers need stable nested metadata shape.
